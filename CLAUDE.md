# CLAUDE.md — ezeraiser/helium-windows

Context for Claude Code sessions working in this repo. Read this before making
changes, especially to `build.py` or `helium-chromium/patches/`.

## What this fork is

This is `ezeraiser`'s fork of the Helium browser (imputnet's ungoogled-chromium
derivative), used together with a fork of the upstream `helium` repo as a
submodule at `helium-chromium/`. Unlike imputnet's upstream, which ships an
`AGENTS.md`/`CLAUDE.md` in `helium-chromium` explicitly forbidding AI-agent
contributions, **this fork intentionally allows and uses Claude Code** — those
restriction files have been deliberately deleted here (see "Sync workflow"
below for what to do when they reappear).

**Sync direction is one-way: we only ever pull from imputnet, never push.**
The `imputnet` git remote in `helium-chromium` exists for `fetch` only. All of
our own commits go to `ezeraiser/helium` and `ezeraiser/helium-windows`.

## Repo layout and the `ezer/` convention

- **`helium-windows`** (this repo): build orchestration only — `build.py`,
  packaging/signing (`package.py`, `signing.py`), and `patches/` for
  Windows-specific patches. Should stay as stable as possible; browser feature
  work does not belong here.
- **`helium-chromium`** (submodule, `ezeraiser/helium`): **not a full Chromium
  source checkout** — it only contains `patches/` (ungoogled-chromium +
  helium's own patches + our `ezer/` patches, listed in `patches/series`),
  `pruning.list`, `domain_substitution.list`, etc. The real `chrome/`,
  `components/`, `content/` tree is generated by `build.py` at build time: it
  downloads a pristine Chromium checkout matching `chromium_version.txt` and
  applies every patch in `patches/series`, in order, into `build/src`.
- **Custom features live in `helium-chromium/patches/ezer/`**, a dedicated
  patch series applied *last* (end of `patches/series`), kept isolated from
  Helium's own patches specifically to minimize merge-conflict surface on
  every imputnet sync. Never fold custom logic into an existing `helium/*` or
  `ungoogled-chromium/*` patch — add a new file under `patches/ezer/` instead.

## What's been added so far (in `patches/ezer/`)

- **`vertical-tab-strip-collapse-settings.patch`** — two new Settings toggles
  under *Browser layout → Vertical*: "Show sidebar as icons only" and "Expand
  on hover (restores last size)", the second disabled unless the first is on,
  both disabled while Frameless/Zen mode is active. Adds a new pref
  (`helium.browser.vertical_expand_on_hover`) and wires it into
  `VerticalTabStripStateController`, whose expand-on-hover logic Helium's own
  `core.patch` had stubbed out (`SetExpandOnHoverEnabled` was a no-op) when it
  moved vertical-tabs state onto its own `kHeliumLayout` pref.
- **`disable-crashpad-engine.patch`** — Crashpad's handler process no longer
  spawns by default (no background `--type=crashpad-handler` processes,
  `CrashReporterClient` still gets registered so nothing else null-derefs).
  Opt back in via `chrome://flags` → "Enable Crashpad crash reporting engine"
  (Windows only).
- `helium/hop/disable-password-manager.patch` was **removed** from the Helium
  patch set (it force-disabled Password Manager via an opinionated policy
  provider).

## `build.py` reliability fixes

Several of these look unnecessary until you hit the exact Windows/CIPD
failure mode they exist for — don't remove them without reproducing the
original bug first:

- **`_clear_readonly_tree()`** — CIPD/npm mark installed files read-only,
  which makes `git clean` (run by `clone.py` on every build) fail with
  "Directory not empty" instead of deleting them. Cleared proactively right
  before `clone.py` runs.
- **`_stash_toolchain_caches()` / `_restore_toolchain_caches()`** —
  `third_party/rust-toolchain` and `third_party/llvm-build` are untracked
  (DEPS-downloaded) and get wiped by every `clone.py` reset, even though they
  carry their own version stamp and would otherwise skip re-downloading
  multi-GB toolchains when the version hasn't changed. Now moved out of
  `build/src` before the reset and back in after.
- **`_unpack_downloads_resilient()` / `_clear_stale_extraction_staging()`** —
  a previous interrupted build can leave a half-moved extraction staging
  directory behind in DEPS-downloaded (git-untracked) `third_party/*`
  folders; a fresh extraction attempt then fails with `FileExistsError`
  (sometimes a bare one with no filename, from the extractor's own
  "already exists" precheck). Cleared before every attempt, not just once.

## `check_ezer_patches.py`

Run this after every imputnet sync (fetch + fast-forward/merge in
`helium-chromium`), **before** kicking off a full build:

```
python check_ezer_patches.py
```

It resets an existing `build/src` checkout to a clean `chromium_version`,
applies every *non*-`ezer` patch as a baseline, then strictly dry-run checks
only `patches/ezer/*.patch`. Catches a broken ezer patch in minutes instead of
after a multi-hour clone+build cycle. Requires `build/src` to already exist
(run `build.py` at least once first).

## Hard-won rules for writing/editing `patches/ezer/*.patch`

CI (`helium-chromium/.github/workflows/ci.yml`, job `validate-with-source`)
runs `devutils/validate_patches.py -l chromium_src`, which is **far stricter**
than the real GNU `patch` that `build.py` uses. Getting a patch to apply
locally is not proof it will pass CI. Specifically:

1. **Zero offset-search or fuzz tolerance.** `validate_patches.py` seeks to
   `hunk.target_start - 1` literally — no searching nearby, no partial-context
   matching. Real GNU `patch`, by contrast, will happily apply a hunk with a
   *wrong* line number via offset search, and can even silently fuzzy-match
   your content into a different-but-harmless location in the file. A patch
   that "just works" locally can still be byte-inaccurate and fail CI.
2. **Every hunk needs trailing context, not just leading context.** A hunk
   that ends exactly on its last inserted line — even with mathematically
   correct old/new hunk-header counts — can fail to apply (observed with GNU
   patch 2.7.6). Always include a few unchanged lines *after* the insertion,
   the same way a real `diff -u` always does by default. This was the root
   cause of a long, confusing CI failure loop on `settings_strings.grdp`: the
   content and line number were both correct, but there was nothing after the
   insertion to anchor the end of the hunk.
3. **Don't hand-count line numbers against `build/src`.** It reflects real GNU
   patch's fuzzy tolerance, which does not necessarily match the strict
   validator's cumulative state. Instead:
   - Let a diff tool compute the hunk for you: reconstruct the "before" text
     by reverse-applying your hand-written hunk via content search (not line
     numbers), then diff that against the real "after" text with Python's
     `difflib.unified_diff` (or real GNU `diff`).
   - Or apply just the chain of patches that touch your target file, in
     `patches/series` order, onto a genuinely pristine checkout — either a
     fresh `helium-chromium/utils/clone.py -o <dir>`, or (much faster, no
     network) `git worktree add --detach <dir> HEAD` from an already-cloned
     `build/src`. Set `core.autocrlf=false` first, or recreate the worktree if
     you forgot — Windows' default autocrlf will otherwise convert LF to CRLF
     on checkout and cause spurious mismatches unrelated to your actual patch.
   - For a quick single-file pristine reference without needing the whole
     `deps.ini` tree: `git show HEAD:<path>` inside `build/src` (if it exists)
     returns the pristine pre-patch blob directly.
4. After any fix, sanity-check header arithmetic (`old_start,old_count
   +new_start,new_count`) against the actual `+`/`-`/` ` lines in the hunk —
   most of the failures in this history were simple count or line-number
   drift, not logic errors.

## CI structure

- `helium-chromium/.github/workflows/ci.yml`: `code-check`/`validate-config`
  are plain lint; **`validate-with-source`** is the job that matters for
  `patches/ezer/*` — it builds a pristine `chromium_src` and runs
  `validate_patches.py` strictly against it.
- `helium-chromium/.github/workflows/lint.yml`: also regenerates
  `i18n/source.gen.json` (via `devutils/i18n.py generate`) and diffs it
  against the committed copy — re-run that command and commit the result
  whenever a `patches/ezer/*` hunk changes a `.grd`/`.grdp` message.
- `helium-windows/.github/workflows/main.yml` (+ `build-steps.yml`,
  `build-stage.yml`): the actual Windows build/package/sign pipeline,
  `workflow_dispatch` only. Azure Trusted Signing secrets are **optional** —
  `signing.py` falls back to producing unsigned packages when they're absent,
  since forks don't have them configured.

## Sync workflow with imputnet

1. In `helium-chromium`: `git fetch imputnet --tags`, then fast-forward/merge
   the target tag or `imputnet/main` into `main`. Never add `imputnet` as a
   push remote or open a PR against it.
2. If `AGENTS.md`/`CLAUDE.md` reappear (imputnet restricts AI-agent use
   there), delete them again — this fork doesn't follow that restriction.
3. Run `python check_ezer_patches.py` from `helium-windows` to catch drift in
   our own patches before committing to a full build.
4. Fix any broken `patches/ezer/*` hunks (see rules above), regenerate
   `i18n/source.gen.json` if needed.
5. Commit in `helium-chromium`, push to `ezeraiser/helium`; bump the submodule
   pointer in `helium-windows` and push to `ezeraiser/helium-windows`.
